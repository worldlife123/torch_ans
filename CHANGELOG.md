# Changelog

All notable changes to this project will be documented in this file.

The format is based on "Keep a Changelog" and this project adheres to semantic versioning.

## [Unreleased]

### Added

- **tANS** (the table-driven ANS coder, FSE style) as a new family of operators, ported from the reference implementation in `3rdparty/ans/tans.cpp`/`tans.hpp`: `tans32` (uint32 state, uint16 stream words, `freq_precision <= 15`), `tans16` (uint16 / uint8, `<= 15`) and `tans8` (uint8 / uint8, `<= 7` — the small-table tier), each with `tans*_init_stream` / `tans*_push` / `tans*_pop`, plus the shared host-side table builder `tans_build_tables(cdfs, cdfs_sizes, table_log)`. A coder is selected with `impl="tans32" / "tans16" / "tans8"` and otherwise drives the existing high-level API unchanged: `table_log` is `freq_precision`, so torch_ans' quantized cdf (which is already a normalized counter — every symbol owns at least one unit, the last entry is `2**freq_precision`) is spread into the FSE tables directly and `init_params` builds them once. Both directions live in one table tensor, which is why it travels in the `cdfs` slot of push *and* pop. A fixed-width tANS state cannot absorb the bits it does not emit, so those live in a stream header (one state word per interleave lane, then the residual bit buffer and its bit count) that is part of the serialized byte string — that is what keeps the stream layout, `rans_stream_to_byte_strings`/`rans_byte_strings_to_stream`, the capacity contract and the whole `TorchANSInterface` surface identical to rANS (`pop` writes the header back, so sequential pops walk the pushes back like `rans_pop` does). Bypass coding, `offsets`, per-symbol distributions, batched states and multi-push streams all work. `tests/test_tans.py` pins the table invariants (spread counts, state ranges, `symbolTT`), the round-trips across alphabets / precisions / bypass, sequential pops, the byte-string path, the high-level API and the caps. Limitations: no `alias_sampling` / `inverse_cdf_precision` variant — the tANS table *is* the symbol lookup — and the interleaved variants run on the CPU and the GPU alike (see the two entries below). See the README's [tANS section](README.md#tans-table-driven-ans) for the memory trade-off (`3 * 2**freq_precision + 2 * cdf_row` int32 per distribution).
- **Interleaved tANS** (`num_interleaves` 1/2/4/8/32): `tans{32,16,8}_i2_push|pop`, `_i4`, `_i8`, `_i32`, selected exactly like the rANS ones (`TorchANSInterface(impl="tans32", num_interleaves=4)`). One state per lane in the stream header, with the bit buffer *shared* by the lanes — the tANS counterpart of rANS' single shared stream cursor, and what keeps a 1-lane stream byte-for-byte what it was (the header is `num_interleaves + 2` words, so its length word is `4 * (num_interleaves + 2)` bytes: 12 at one lane). The lane of a symbol is its index % `num_interleaves` and the two directions walk the lanes in mirrored order, so the leftover head/tail of a symbol count that is not a multiple of the lane count is handled by the same head/tail structure `rans_cpu.cpp` uses. `tans_init_stream` accepts 1/2/4/8/32 (32 is the full-warp group of the CUDA interleaved kernels below; the CPU kernels implement it from the same lane loop, exactly like the rANS 32-way). The Python side follows: `_STREAM_SIZES`' first component is now "state bytes per lane" with `_TANS_HEADER_EXTRA_BYTES` added once, so the capacity contract adopts the right initial length word. Measured with the new `scripts/bench_tans_vs_rans.py` (see `benchmark_status.md`): on the CPU interleaving pays off *more* for tANS than for rANS once the table leaves the cache — up to ~2.6x encode / ~2.2x decode at `freq_precision=15` with 8 lanes, ~1.2x at `freq_precision=7`.
- `torch_ans/stream_capacity.hpp`: the worst-case stream growth and the caller-owned-capacity compare/grow, extracted from `rans_push` so that `tans_push` shares one implementation instead of adding a third copy of the arithmetic. `utils._stream_budget` (Python) and `tests/test_capacity_contract.py` are unchanged, and the tANS families were added to that test's matrix.
- Compile gates `TORCH_ANS_WITH_TANS32` / `_TANS16` / `_TANS8` (one per family, like the rANS ones) so an incremental build compiles only the families an interface asks for. `tans_build_tables` is deliberately *not* gated — all three families share the result — and is part of `COMMON_OPS`. The tANS push/pop instantiation macros now take the interleave factor and are gated by the shared `TORCH_ANS_WITH_INTERLEAVE_2/4/8/32`.
- `scripts/bench_tans_vs_rans.py`: the tANS vs rANS comparison (family × `num_interleaves` × `freq_precision` × alphabet × bypass), which reports encode/decode throughput *together with* bits/symbol (against the entropy of the distribution the symbols were drawn from) and the per-distribution table size — tANS "faster" must never be read without the compression and memory cost next to it. Configurations a family cannot code (an alphabet that does not fit `2**freq_precision` slots, or a precision above the family cap) are skipped with the reason printed, and every measured configuration is round-trip checked before it is timed. Raw results: `benchmarks/tans_vs_rans_cpu.json`; the numbers are in `benchmark_status.md`, including a supplement for `tans8` at `freq_precision=7` (its cap and its whole regime) across alphabets 16/32/64/127 and 256/4096 distributions (`benchmarks/tans8_fp7_cpu.json`, `benchmarks/tans8_fp7_many_dists_cpu.json`): 8 lanes reach 85–95 MB/s encode / 99–103 MB/s decode at 256 distributions (1.19–1.28× / 1.09–1.22× the one-lane numbers) and 1.55× / 1.74× at 4096, while decoding 1.26–1.46× faster than the fastest rANS at the same precision. `scripts/bench_interleaves_cpu.py` now covers the tANS families too.
- **tANS on CUDA** (`torch_ans/tans_cuda.cu`): the three tANS families now code device tensors, so `impl="tans32" / "tans16" / "tans8"` works on a GPU through the same operator names, the same stream layout and the same capacity contract as before — `tans_push` / `tans_pop` route on the tensor device (tans.hpp) and the CUDA kernels are the CPU path verbatim: one thread per stream row at one lane, one lane group per row above it (see the warp-kernel entry below) — so a stream coded on one device decodes on the other **byte for byte** (`tests/test_tans.py` compares the coded payloads, not just the decoded symbols, for every interleave factor). `TorchANSInterface.init_params` builds the table on the host for every tANS interface and moves it to `self.device` (the builder is host-only, like the alias table), which is what makes the device path work at all.
- **Warp-level interleaved tANS kernels on CUDA** (`torch_ans/tans_warp_cuda.cuh`): `tans{32,16,8}_i2/i4/i8/i32_push|pop` now code device tensors too, so `num_interleaves` 2/4/8/32 behaves the same on both devices - one *lane group* of `num_interleaves` lanes codes one stream row, each lane owning its state while the bit buffer and the payload cursor stay shared (a fixed-width tANS state cannot absorb the bits it does not emit). `tans_push` / `tans_pop` keep their single entry point: `tans_cuda.cu`'s launcher routes `NUM_INTERLEAVES > 1` to the warp kernels, and `tans_init_stream` now accepts 32 (the CPU kernels instantiate it from the same lane loop, like the rANS 32-way). The per-lane table work runs in parallel (encode: `symbolTT` + `nextState`; decode: the two decoder planes - the divergent loads the warp amortises, plus coalesced `symbols`/`indexes` reads at consecutive indices that the one-thread-per-row kernel cannot have), while the bit layer is committed in lane order (push lane N-1→0, pop lane 0→N-1) by broadcasting each lane's field with `__shfl_sync` and letting every lane apply the identical update (only lane 0 stores the flushed word; the bypass digits are the sequential exception and are skipped entirely by one `__ballot_sync` when no lane is a sentinel). The payload is therefore **bit-identical** to `tans_cpu.cpp`'s interleaved path at every factor, head/tail included, so an interleaved stream can be coded on one device and decoded on the other - `tests/test_tans.py` compares the byte strings and cross-decodes in both directions, alongside bypass, padding indexes, non-multiple symbol counts, batches that do not fill a block, the staging A/B and the high-level API (which also pins the 32-lane capacity contract: a 32-lane header is 136 bytes). Measured on an RTX 2080 Ti (4M symbols, 64 distributions, table in global memory; `benchmarks/tans_interleaved_cuda.json`, and the staging A/B in `benchmarks/tans_interleaved_cuda_smem_{off,on}.json`): at 8 stream rows 4 lanes lift `tans32` at `freq_precision=7` from 19.1/28.3 to 29.5/41.5 Msymbol/s encode/decode (**+54%/+47%**), 8 lanes to 30.1/40.7 (**+58%/+44%**); with 512 rows the gain is +29%/+29% (4 lanes) and with 4096 rows it flattens to ~+6%/+5%. 32 lanes is *slower* than 4-8 in most configurations (the shared bit layer is filled by 32 sequential appends per group, and the 136-byte header costs ~1.1 bit/symbol on a 1024-symbol row), and the rANS `rans32_16` 32-way warp path remains 5-12x faster at a tiny batch and up to 1.8x at 512 rows - it needs no shared bit layer, which is the structural difference between the two families. Table staging stays enabled and is a small win where it triggers (+1-6% encode, up to +18% decode at the widest group with 1024-symbol rows). `scripts/bench_tans_vs_rans.py` now takes `--parallel-states` as a sweep (the batch is the dimension that decides whether interleaving pays), adds `--warp-block-threads` (`TORCH_ANS_TANS_WARP_BLOCK_THREADS`) and reports a `ps`/`wblk` column plus a "tANS vs rANS at 32 lanes" section; the tables and the full discussion are in `benchmark_status.md`.
- **Shared-memory table staging for the tANS CUDA kernels**: a tANS lookup *is* its table, and every symbol reads it at a state- or symbol-dependent offset, so the kernel stages the whole table (`num_dists * (3 * 2**freq_precision + 2 * cdf_row)` int32 words) into shared memory when it fits `TORCH_ANS_TANS_SMEM_BUDGET` (default 16 KiB per block, `0` disables it; `rans_warp_cuda.cuh`'s A9 staging is the same pattern, including the compile-time `USE_SHARED_TABLE` switch and the whole-table-or-nothing rule). `TORCH_ANS_TANS_BLOCK_THREADS` overrides the launch block size, which is otherwise derived from the batch size: one thread codes one row, so the block size decides how many SMs get work (measured: a fixed 64-thread block put 1024 rows on 16 blocks and lost ~18% decode against 8 threads per block) *and* how often the staging copy is paid (it is per block). See `benchmark_status.md` for the measurements, which include the low-distribution sweeps (8 and 4 distributions, where the table *does* fit: `benchmarks/tans_vs_rans_cuda_dists{8,4}_smem_{on,off}.json`, plus the long-stream pair `benchmarks/tans_vs_rans_cuda_longrows_smem_{on,off}.json`) with the rANS families present as the baseline: with 1024-symbol rows the staging is a wash or slightly negative (0.92-0.97 of the global path - the copy is paid per block and 6-24 KB of shared per block lowers occupancy, while L1 already serves a table that size), while with few blocks and long streams (64 streams × 16K symbols, a 6.6 KB table) it is **+4.6-5.4% encode / +3.1-3.6% decode**. In the same small-table regime single-lane tANS decodes 1.15-1.33× faster than single-lane rANS (2.3× with long streams).
- `scripts/bench_tans_vs_rans.py --device cuda` (plus `--smem-budget`, `--block-threads`, a `smem` column and device/knob fields in the JSON), the raw results in `benchmarks/tans_vs_rans_cuda.json`, `benchmarks/tans_cuda_staging_off.json` / `benchmarks/tans_cuda_staging_on.json`, `benchmarks/tans_vs_rans_cuda_dists{8,4}_smem_{on,off}.json` and `benchmarks/tans_vs_rans_cuda_longrows_smem_{on,off}.json`, and the measured comparison in `benchmark_status.md`: with 1M symbols, 1024 rows and 256 distributions on an RTX 2080 Ti, single-lane tANS decodes 1.0–1.5× faster than **single-lane** rANS at `alphabet >= 64` (up to 1.54× at alphabet 256 / `freq_precision=10`) while encoding within ±5% of it; the rANS 32-way warp path remains the fastest configuration overall (1.2–2.0× over tANS on decode, 1.25–1.5× on encode), at the cost of ~0.6–0.8 bit/symbol on 1024-symbol rows because each of its 32 lanes flushes its own state per row — for the tANS-side interleave gain on the device, and why 4-8 lanes beat 32 there, see the warp-kernel entry above.

### Fixed

- `STD_TORCH_CHECK` (the ATen backend's one check macro) now forwards its arguments verbatim (`TORCH_CHECK(__VA_ARGS__)`) instead of appending the variadic part to a spelled-out condition. The common single-argument call `STD_TORCH_CHECK(cond)` expanded to `TORCH_CHECK(cond, )`, whose empty trailing argument only compiles on the newer torch releases; on torch 2.7 it fails with "expected primary-expression before ')' token" from `c10/util/Exception.h`, which made every build against that release fail before it reached a kernel (the CUDA 11.8 toolchain that matches this machine's nvcc is a torch 2.7 environment here). Behaviour is unchanged wherever the macro already compiled.
- `scripts/bench_tans_vs_rans.py` now documents which `torch_ans` it measures. Run as `python scripts/bench_tans_vs_rans.py`, `scripts/` becomes `sys.path[0]`, so the script imports the *installed* package - an older install silently shadows the working tree (the first CUDA run here died with `NotImplementedError: Unknown impl tans32` for exactly that reason). Measuring the sources needs `PYTHONPATH=$PWD python scripts/bench_tans_vs_rans.py`.

## [0.4.0] - 2026-09-16

v0.4.0 completes the libtorch **stable ABI** migration: the native code can be compiled once against the stable
ABI (`TORCH_TARGET_VERSION` = torch 2.10), so one `.so` serves every `torch >= 2.10`, and that path is preferred
whenever a prebuilt extension is present. Source installs and `torch < 2.10` are unchanged - they keep compiling
per torch exactly as before. The four ways to handle stream capacity were all weighed: keeping the
`aten::resize_` dispatcher call (removes neither of the two costs it has), the Python capacity contract
(adopted), having the operator return a grown stream (changes the public signature and every call site) and a
strict pre-reservation that raises instead of growing (loses push's self-growing behaviour for direct callers);
`scripts/bench_stream_capacity.py` measures what the adopted one buys.

### Added

- A prebuilt libtorch-stable-ABI wheel. `WITH_STABLE_ABI=1 pip install . --no-build-isolation` builds `torch_ans/_C_cpu.so` (all 71 schemas plus the CPU and catch-all implementations); adding `WITH_CUDA=1` also builds `torch_ans/_C_cuda.so`, which registers implementations only - a second schema declaration is rejected by the dispatcher. Both libraries export no CPython and no ATen/C++ symbols (only the stable C shim's `aoti_torch_*`/`torch_*`), which is what makes them independent of the torch release and the Python version; the wheel is therefore tagged `py3-none-<platform>`. `torch_ans/_stable_C.py` finds and loads them with `torch.ops.load_library`, ahead of any compilation, and every failure mode (old torch, missing/unloadable file, CUDA request without a CUDA library) is a warning plus the normal runtime build rather than an error. `TORCH_ANS_NO_STABLE_ABI=1` and `TORCH_ANS_STABLE_LIB_DIR` control the lookup; `incremental_compile=` has no effect on this path (the prebuilt extension has every operator).
- `torch_ans/ta/`: the compatibility layer between the ATen build and the stable-ABI build (`torch_api.hpp` plus one header per backend and the POD `view.hpp`), so kernels and op wrappers exist once and both build modes are bit-comparable. Compile-checked in both modes and with nvcc by `scripts/check_ta_headers.py` / `tests/test_ta_headers.py`.
- `scripts/check_stable_abi_wheel.py` (wheel shape, `nm -D -u` symbol whitelist, `readelf -d` NEEDED check) and `scripts/bench_stream_capacity.py` (the per-push cost of the capacity contract, before/after) - the measured numbers are in the capacity-contract entry below.
- Tests for the new path: `tests/test_stable_abi.py` (registration, CPU/CUDA bit equality, the Python `bytes` operators, the CUDA flavour incl. warp-32 and the sparse inverse-CDF table), `tests/test_capacity_contract.py`, `tests/test_cross_version_load.py` (one wheel, several torch versions, one digest).
- CI in `cibuildwheel.yml`: `build-stable-wheel` (build, retag to `py3-none-<platform>`, symbol whitelist, then "install it and check that using it compiles nothing"), `cross-version-load` (torch 2.10 / the build version / the newest release) and `cross-version-compare` (all digests must agree). The matrix floor is asserted against `_stable_C.STABLE_ABI_MIN_TORCH` by a test, so CI cannot drift below the ABI the `.so` targets.

### Changed

- Stream capacity is now a contract between Python and the native push. `TorchANSInterface` reserves the capacity (`utils._stream_budget`, a port of the wrapper's worst-case arithmetic, pinned against it by `tests/test_capacity_contract.py`) and passes it as the new trailing `used_bytes` argument; with it the wrapper only compares and raises instead of reading the stream's length word back and resizing. That removes a blocking device->host copy from every CUDA push (measured 157 -> 39 us per small push; the CPU side 21 -> 12 us) and keeps `aten::resize_` - whose schema the stable ABI does not promise - out of the hot path and out of the prebuilt library. Omitting `used_bytes` (the default, -1) keeps the previous behaviour bit for bit, so direct operator calls, existing scripts and extensions compiled before this release are unaffected; `tests/test_capacity_contract.py` covers that fallback too.
- The native operator set, the pybind11 bindings and the stable schemas/implementations are now declared side by side in `ans_bindings.hpp`, with `lib.cpp` (CPU flavour: schemas + catch-all + CPU implementations) and the new `lib_cuda.cpp` (CUDA flavour: implementations only) as the two entry points. `pybind11` is no longer a build or runtime dependency: the ordinary build takes the headers from torch itself and the stable build needs none.
- `tests/test_warp_cuda.py::test_high_level_rans32_16_impl_resolution` compares the resolved encoder against the module the interface actually resolved, instead of against `torch_ans._C` (a different module whenever a compiled extension and a prebuilt one coexist).

### Fixed

- CUDA kernels now launch on torch's current stream (`ta::current_stream`) instead of stream 0, which was a race with any non-default `torch.cuda.Stream()` and made coding invisible to stream ordering, and a launch error is checked (`cudaGetLastError`) instead of surfacing on the next unrelated CUDA call.
- macOS runtime builds no longer abort the process on the first parallel operation. The OpenMP variant they get from Homebrew libomp links and imports perfectly well and then dies - SIGABRT inside `rans_pmf_to_quantized_cdf`, no exception, nothing a build- or load-time check could see - with torch 2.14 (2.13 and older work), which turned the full-matrix macOS arm64 jobs red. As the crash is invisible to the build, the runtime build now runs that operator once in a child process (a build cache hit plus one call) before accepting the variant, and falls back to the flags without a second OpenMP runtime - the ones `setup.py` has always used on macOS, with `at::parallel_for` on torch's own thread pool instead of a second runtime. The outcome is remembered in an `openmp_build_state` file in the torch extensions cache directory; delete it to try OpenMP again.

### Removed

- `ta::safe_stream_byte_length` / `ta::ensure_stream_capacity`: an unused second copy of the stream-growth arithmetic (only the header syntax check instantiated it) that would have had to stay in step with the native wrapper and the Python budget by hand.

## [0.3.0] - 2026-09-14

v0.3.0 includes a major performance overhaul for both CPU and GPU.

### Added

- Warp-level 32-way interleaved rANS coding on CUDA for `rans32_16` (`rans32_16_i32_*`), one warp sharing a single bitstream cursor, bit-compatible with the CPU interleaved layout. Also fixed the broken 4-way CUDA interleaved path (routed to 4-lane sub-warp kernels; other variants raise a clear error), exposed `num_interleaves` in `TorchANSInterface`, and fixed `impl="rans32_16"` being shadowed by the `"rans32"` prefix match.
- Runtime-build fallbacks so a compiled extension is never a dead end: an extension that cannot be imported (compiled against another torch) falls back to compiling one for the local torch instead of failing the import, and a CPU-only extension that is asked to code CUDA tensors warns and compiles a CUDA extension locally - or raises with the exact commands to fix the toolchain instead of a bare "not compiled with GPU support" from C++. The new `TORCH_ANS_FORCE_RUNTIME_BUILD=1` ignores any pre-built extension and always compiles for the local torch.
- A sparse inverse-CDF symbol lookup for decode (`inverse_cdf_precision` int or `"auto"`): `2**q`-entry table plus a bounded walk, staged into shared memory on the CUDA 32-way warp path (decode ~6 -> ~26 Gsymbol/s on RTX 2080 Ti). Also fuses `pmf -> quantized cdf` and `cdf ++ inverse table` into single-pass implementations (2-4x faster `init_params`), adds the missing `rans64_i4_invcdf_pop` binding.
- Interleaved variants of the alias-sampling coder (`*_alias_i2/i4/i8_*`, new `alias_sampling=True` option), with batched symbol lookup; `rans_alias_build_table` now fails loudly on invalid input.
- `scripts/bench_version_matrix.py` (raw-operator matrix: device x family x `num_interleaves` x symbol lookup, plus the `init_params` build steps and the high-level API; driven through the low-level ops so operators that exist in only one release are reported as `n/a` instead of failing, and every configuration is round-trip checked before it is timed) and `scripts/generate_benchmark_report.py`, which renders `benchmark_status.md` from two of its JSON outputs. `benchmark_status.md` now holds a measured v0.2.1 -> v0.3.0 comparison (i7-6800K / RTX 2080 Ti): CPU decode 1.27-1.44x at the default configuration and 2.40-2.75x at `num_interleaves=4`, CUDA 1-way unchanged, new CUDA 32-way warp path at ~26 Gsymbol/s, `pmf -> cdf` 6-11x faster and inverse-CDF table build 60-600x faster.

### Changed
- Lazy compile is upgraded to incremental (per-interface) JIT build: `TorchANSInterface` now compiles only the operators its configuration needs, nothing before first use (new `incremental_compile=True` argument, `TORCH_ANS_INCREMENTAL_COMPILE=0` to disable). Bindings are gated by `TORCH_ANS_WITH_*` macros in `ans_build_config.hpp` / `ans_bindings.hpp`, with matching explicit instantiations in `rans_cpu.cpp`/`rans_cuda.cu`.
- CPU interleaved coding is now much faster: ~1.25-1.4x encode / ~1.8-2.1x decode at `num_interleaves=4` (previously a slight slowdown). Achieved via branch-free renormalization, pipelined division (`rans_divmod`), and register-resident interleaved states (see `rans_cpu.cpp` / `rans_utils.hpp`).
- New default symbol lookup is branch-free (monotone predicate search), removing binary-search mispredicts in non-interleaved decoding.
- Inverse-CDF table gap closing is branch-free (`rans_invcdf_advance`, fixed `RANS_INVCDF_WINDOW`=2 parallel loads), making the table the fastest CPU decode lookup at every alphabet size. `num_interleaves=32` remains CUDA-only.
- Package metadata now comes from `pyproject.toml` (PEP 621, `setuptools>=61`), including the project URLs. `setup.py` only mirrors it when the installed setuptools is older than 61, which ignores `[project]` entirely - that is the `pip install . --no-build-isolation` case, where dropping the mirror would silently produce an `UNKNOWN` distribution with no dependencies. `tests/test_packaging_metadata.py` keeps the two in sync.
- The extension compiled at install time is described by a compiled-in `_torch_ans_with_cuda` flag (see `lib.cpp`) rather than by generated metadata, so the Python layer can tell whether the loaded build can code CUDA tensors.

### Fixed

- CUDA build failed to import (`undefined symbol`) for `*_i2_*`/`*_i8_*` and interleaved alias/inverse-CDF combinations due to missing CUDA instantiations; all bound combinations now have one, unsupported ones raise a clear error (interleaved CUDA coding is rans32_16-only).
- The sdist could miss the native headers it needs to build (`ans_bindings.hpp`, `ans_build_config.hpp`): setuptools does not recompute the manifest when new source files appear, and the file list was never declared. `MANIFEST.in` now lists the sources explicitly and excludes generated or stale artifacts (`torch_ans/_torch_build_version.py`, `*.so`) so a leftover local `_C*.so` can never shadow `torch_ans/_C.py` in a distribution.
- Importing the Python API stays lazy when no compiled extension is present. The import machinery probes `__path__` on the module it is about to import names from (`from ._lazy_C import ...`), and the shim answered that probe with a full build, so a plain `import torch_ans.utils` compiled the whole extension - CUDA included - before any use. Dunder probes now raise `AttributeError` without building, while `from torch_ans._C import <op>` still compiles the full extension as documented.

### Removed

- The CI-generated benchmark table: the full-matrix workflow no longer runs `pytest-benchmark`, no longer uploads benchmark artifacts and no longer commits `benchmark_status.md` (it now only commits `build_status.md`); `tests/test_benchmarks.py`, `scripts/generate_benchmark_status.py` and the `pytest-benchmark` dev dependency are gone. The runners are virtualised CPUs whose throughput varies by tens of percent between runs, so the table could only ever show virtualisation noise rather than a regression. `benchmark_status.md` is measured locally on real hardware and committed instead.


## [0.2.1.post1] - 2026-09-07

- Packaging fixes surfaced by the v0.2.1 CI run: supply `-std=c++17` only for torch 1.x (torch >= 2.x selects its own C++ standard, up to C++20 for newer releases, and a user-supplied `-std=` would override it), silence Xcode 16's `-Winvalid-specialization` error for torch 2.7 headers on macOS, and skip `brew update` in CI.
- Fix runtime build on machines where every CUDA configuration fails: the `cuda_build_state="cpu"` shortcut no longer compiles the CPU-only extension with `-DWITH_CUDA` (it produced a `.so` with undefined symbols that failed to load and forced a second, pure-CPU rebuild on every fresh import — ~76s per process). Also pass `-DWITH_CUDA` to nvcc explicitly (torch only forwards `extra_cflags` to the C++ compiler and, unlike `WITH_HIP`, does not define it itself), so a successful CUDA toolchain no longer goes undetected.

## [0.2.1] - 2026-09-07

- (Beta) Add lazy compile mode during installation: Users can now directly use `pip install torch_ans` without `--no-build-isolation` to skip building when install. In this case the building will occur during first-time import. A dedicated `lazy-compile-test` CI job covers this flow on Linux/Windows/macOS, and the runtime build works around the nvcc <= 12.1 vs GCC >= 11.4 libstdc++ header incompatibility (see README Known Issues).
- Runtime dynamic build: platform-appropriate compile flags (MSVC / Apple clang / GCC), OpenMP kept enabled so `at::parallel_for` stays multi-threaded for CPU coding (with Homebrew libomp support on macOS), and build results cached in the torch extensions directory.
- Add index range check in C++/CUDA rans_push/pop code, improving its stability and reduce "Segmentation fault" issues.
- Fix cached encode in high-level API: adding CompressAI params to encode queue, and properly reset cache after flush.
