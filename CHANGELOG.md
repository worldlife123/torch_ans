# Changelog

All notable changes to this project will be documented in this file.

The format is based on "Keep a Changelog" and this project adheres to semantic versioning.

## [Unreleased]

- Compile only what an interface needs in the runtime (JIT) build. `TorchANSInterface` now resolves its operators from a module built for its own configuration: `impl="rans64"` with the default settings compiles the `rans64` push/pop plus the shared helpers instead of all three rANS variants with every interleave factor and symbol lookup (measured 25s vs 100s of the same CPU-only build, and the CUDA side shrinks correspondingly). Each configuration gets its own cached module (`torch_ans_C_r64`, `torch_ans_C_r64_i4_invcdf`, ...), a module that already exports the requested operators is reused (the full build satisfies every configuration), and nothing is compiled before the first operator is actually used - importing `torch_ans.utils` or `torch_ans._C` alone no longer triggers a build. New `TorchANSInterface(incremental_compile=...)` argument, on by default; `TORCH_ANS_INCREMENTAL_COMPILE=0` disables it and compiles every operator up front (which is also what a pre-built `torch_ans._C` always contains). Implementation: the bindings moved from the `TORCH_EXTENSION_RANS_BINDINGS` macro into `torch_ans/rans_bindings.hpp` and are gated by `TORCH_ANS_WITH_{RANS64,RANS32,RANS32_16,INTERLEAVE_*,ALIAS,INVCDCDF}` (`torch_ans/rans_build_config.hpp`), the profiles being derived in `torch_ans/_dynamic_build.py`. The `TORCH_LIBRARY_IMPL` blocks in `rans_cpu.cpp`/`rans_cuda.cu` are gone - they registered nothing reachable (`torch.ops.torch_ans` was always empty, there is no `TORCH_LIBRARY` schema) and only served to force the template instantiations the pybind bindings link against; those are now explicit instantiation definitions, gated the same way (an unused address-taken static does not survive `-O3`, so the old trick could not simply be kept).
- Close the inverse-CDF table's gap branch-free (`rans_invcdf_advance`), which makes the table the fastest CPU decode lookup instead of the slowest. The table entry is a lower bound of the symbol, and the remaining couple of entries used to be resolved with `while (cdf[idx+1] <= cum_freq) ++idx;` — a data-dependent branch that (like the renormalize branch) flushes the out-of-order window the interleaved lanes need. It is now a fixed window of `RANS_INVCDF_WINDOW` (2) cdf entries loaded *in parallel* (they all come from the lower bound, so unlike the walk's loads they do not depend on each other) plus a branch-free count: since the cdf is monotone, the number of window entries `<= cum_freq` is exactly the number of steps the walk would have taken. A loop for the rare remainder (a bucket spanning more than the window) keeps it exact for any distribution — verified identical to the walk over 4.6e10 randomized (cdf row, table precision, query) combinations for window widths 1-6. On the batched interleaved path the window loads are issued step-major across the lanes, like the symbol search. Measured (i7-6800K, 1M symbols, single thread, `num_interleaves=4`, decode cyc/symbol) the table now beats the divided search at every interleave factor: 256 dists x 258 symbols 48.8 vs 55.0, 64 dists x 1026 symbols 52.6 vs 79.8, single distribution 29.3 vs 45.8; window widths 1/3/4 were all worse than 2 (fewer loads per lane matters more than walk coverage — the lanes are limited by outstanding-miss capacity). The default symbol lookup and the alias path are unchanged.

- Make CPU interleaved coding actually deliver: `num_interleaves=4` is now ~1.25-1.4x on encode and ~1.8-2.1x on decode (i7-6800K, 1M symbols, 256 distributions), where the previous implementation was a 0.7-1.0x *slowdown* on all variants. Three changes were needed, all in `rans_cpu.cpp` / `rans_utils.hpp`:
  - **Branch-free renormalization** (`APPEND_STATE_TO_STREAM_IF` / `POP_STATE_FROM_STREAM_IF`): the encode side stores the word into the next slot speculatively and commits the cursor with a `cmov`; the decode side loads unconditionally and selects. The renormalize branch is close to a coin flip and its mispredicts were flushing the out-of-order window the interleaved lanes need. Buffers now reserve one extra word of slack for the speculative store (`rans_init_stream`, `rans_push`).
  - **Pipelined division**: the encode step's `x / freq` and `x % freq` (a non-pipelined integer divider, so N states merely queued on it) are replaced by a floating-point divide plus an integer fix-up that makes the result exact for any input (`rans_divmod`), and the state update uses the `x + q*(2^p - freq) + start` form to keep the remainder off the critical path.
  - **Overlap-friendly loops**: the interleaved states live in register-resident locals instead of in the stream tensor they are written to (every lane access uses a compile-time index via `constexpr_for`), all per-lane table lookups are gathered for the whole interleave group before any state is updated, the symbol search walks all lanes step-by-step instead of lane-by-lane (`rans_pop_indexed_cpu`), and the loop-invariant scalars/accessors are copied into locals inside the `parallel_for` body so gcc cannot assume the stream stores alias them (it used to reload `freq_precision` and the cdf base/stride per lane).
  - The default symbol lookup is now branch-free too (a monotone predicate search with a `cdf_size`-dependent trip count), which also removes the data-dependent binary-search mispredicts for non-interleaved decoding.
- Make the inverse-CDF table decode path branch-free as well, so it becomes the fastest CPU decode configuration at every alphabet size and every `num_interleaves` (previously its gap-closing walk was a data-dependent branch and it lost to the divided search for interleaved coding). `rans_invcdf_advance` replaces `while (cdf[idx+1] <= cum_freq) ++idx;` with a fixed window of `RANS_INVCDF_WINDOW` (=2) cdf entries loaded *in parallel* plus a branch-free count — the window loads all derive from the table's lower bound, so they do not depend on each other the way the walk's serial loads do — and the interleaved decoder closes the gap of all lanes step by step across the group. A loop for the rare remainder keeps the result exact for any distribution. Measured at 256 distributions / alphabet 256: decode 65 -> 50 cyc/symbol at `num_interleaves=4` (and the table now beats the divided search there by ~1.18x), alphabet 4096: 158.9 -> 62.4 cyc/symbol at `num_interleaves=1`. Verified index-identical to the linear walk over 4.6e10 randomized cases.
- `num_interleaves=32` remains CUDA-only in practice (register pressure, ~0.8x on CPU).

- Add interleaved variants of the alias-sampling coder (`rans64/rans32/rans32_16_alias_i2/i4/i8_push|pop`, plus a `alias_sampling=True` option on `TorchANSInterface`) and batch its symbol lookup across the interleaved lanes (it used to fall back to the per-lane generic path, so it could not overlap at all). Two fixes make it scale: the bucket index `cum_freq / cut_size` was a *non-pipelined* 32-bit division per symbol - it is a shift here, because the alias builder only accepts a cdf size of `2**k + 1` so `cut_size` is always a power of two (bit-identical, the shift is recovered from the float exponent of that power of two); and the pop side used to be the one lookup that was not batched. Measured (i7-6800K, 1M symbols, 256 distributions, alphabet 255, p=15): decode 118.2 -> 75.8 cyc/symbol at `num_interleaves=4` (1.56x, against 1.76x for the inverse-CDF table) and 113.8 at 1-way, so alias sampling still ends up the *slowest* of the three lookups - its encode side additionally reads a remap table indexed by the whole `2**freq_precision` range (32 MB for 256 distributions). It stays opt-in.
- Make `rans_alias_build_table` fail loudly when `build_alias_mapping` reports failure (it requires `2**symbol_precision == cdfs_sizes - 1` and frequencies that sum to exactly `2**freq_precision`): the return value used to be ignored, so a table that could not be built was left partially filled and silently produced a wrong stream on every symbol. `TorchANSInterface` now derives the required `symbol_precision` from the cdf size and raises a `ValueError` for an unsupported one.

- Fix the CUDA build: combinations that the CPU side binds in `rans.hpp` had no CUDA instantiation, so the shared library was left with undefined symbols and the whole module failed to import (`ImportError: undefined symbol ...`) whenever it was built with `WITH_CUDA=1`. This affected `*_i2_*`/`*_i8_*` (and the alias/inverse-CDF interleaved variants) for all three rANS variants; all bindings now have a CUDA definition, and the combinations that are not supported on CUDA raise a clear error when called (interleaved CUDA coding is rans32_16-only). The CUDA test suite (18 tests) now runs and passes on an RTX 2080 Ti, including the CPU<->GPU bit-compatibility tests that guard the CPU interleaved coders.
- Fix alias sampling on the interleaved CUDA path: the warp push kernel accepted `USE_ALIAS_SAMPLING_CDF` but never applied the remap, so it emitted a plain rANS stream that decoded to garbage (100% wrong symbols at `num_interleaves=4`); the 1-way path was the only one covered before. It now applies the remap like the CPU/1-way coders, and `tests/test_warp_cuda.py::test_cuda_alias_interleaved_roundtrip` covers both 1-way and 4-way, on GPU and cross-device.
- Measured alias sampling on CUDA (`rans32_16`, RTX 2080 Ti, 1024x4096 symbols, alphabet 255, p=15, 256 distributions, Gsymbol/s encode/decode): divided search 1.16/0.84 at 1-way, 3.69/1.64 at 4-way, 10.10/6.19 at 32-way; inverse-CDF 1.57/1.42, 3.66/2.30, 10.49/8.85; alias 1.01/1.24, 1.98/2.56 (no 32-way variant). So interleaving is worth ~3x at 4-way and ~7-9x at 32-way on GPU, the inverse-CDF table is fastest in both directions, and alias sampling is slower than it at every interleave factor (its decode is faster than the divided search, but its encode is up to 1.9x slower because it reads a 33 MB remap table).

## [0.3.0] - 2026-09-xx

- Add a sparse inverse-CDF symbol lookup for decode (`inverse_cdf_precision`, exposed as `TorchANSInterface(inverse_cdf_precision=int or "auto")`): a `2**q`-entry table plus a bounded linear walk replaces the data-dependent divided-search + binary refine; `"auto"` picks the precision from the alphabet size (and skips the table for alphabets < 64). On the CUDA warp-level 32-way path the whole cdf++table row is staged into shared memory and the bypass "raw value" phase is skipped via a group ballot when no lane needs it: decode throughput on an RTX 2080 Ti (8 rows x 256 symbols, warp 32-way) went from 1.3 to 25.8 Gsymbol/s. Also fuses `pmf -> quantized cdf` and `cdf ++ inverse table` into single-pass implementations (rewritten `rans_pmf_to_quantized_cdf`, new `rans_build_inverse_cdf`) making `init_params` 2-4x faster, adds the previously missing `rans64_i4_invcdf_pop` binding, adds a new symbol lookup strategy to `benchmark.py`, and documents the design, measurements and rejected alternatives in `SPARSE_INVCDF_SUMMARY.md`.
- Add warp-level 32-way interleaved rANS coding on CUDA for the `rans32_16` variant (`rans32_16_i32_push` / `rans32_16_i32_pop` / `rans32_16_i32_invcdf_pop`): one warp's 32 lanes hold 32 interleaved rANS states sharing a single bitstream cursor, coordinated with `__ballot_sync`/`__shfl_xor_sync` (technique referenced from Recoil, encode+decode; see `torch_ans/rans_warp_cuda.cuh`). The CUDA interleaved streams are bit-compatible with the CPU interleaved implementation (same layout and word order), verified by cross-device decode tests. Also fixes the previously broken 4-way CUDA interleaved path (now routed to 4-lane sub-warp group kernels; interleaved CUDA coding is rans32_16-only and other variants now raise a clear error instead of silently mis-coding), adds CPU `NUM_INTERLEAVES=32` instantiations, exposes `num_interleaves` in `TorchANSInterface`, and fixes `impl="rans32_16"` being shadowed by the `"rans32"` prefix match.

## [0.2.1.post1] - 2026-09-07

- Packaging fixes surfaced by the v0.2.1 CI run: supply `-std=c++17` only for torch 1.x (torch >= 2.x selects its own C++ standard, up to C++20 for newer releases, and a user-supplied `-std=` would override it), silence Xcode 16's `-Winvalid-specialization` error for torch 2.7 headers on macOS, and skip `brew update` in CI.
- Fix runtime build on machines where every CUDA configuration fails: the `cuda_build_state="cpu"` shortcut no longer compiles the CPU-only extension with `-DWITH_CUDA` (it produced a `.so` with undefined symbols that failed to load and forced a second, pure-CPU rebuild on every fresh import — ~76s per process). Also pass `-DWITH_CUDA` to nvcc explicitly (torch only forwards `extra_cflags` to the C++ compiler and, unlike `WITH_HIP`, does not define it itself), so a successful CUDA toolchain no longer goes undetected.

## [0.2.1] - 2026-09-07

- (Beta) Add lazy compile mode during installation: Users can now directly use `pip install torch_ans` without `--no-build-isolation` to skip building when install. In this case the building will occur during first-time import. A dedicated `lazy-compile-test` CI job covers this flow on Linux/Windows/macOS, and the runtime build works around the nvcc <= 12.1 vs GCC >= 11.4 libstdc++ header incompatibility (see README Known Issues).
- Runtime dynamic build: platform-appropriate compile flags (MSVC / Apple clang / GCC), OpenMP kept enabled so `at::parallel_for` stays multi-threaded for CPU coding (with Homebrew libomp support on macOS), and build results cached in the torch extensions directory.
- Add index range check in C++/CUDA rans_push/pop code, improving its stability and reduce "Segmentation fault" issues.
- Fix cached encode in high-level API: adding CompressAI params to encode queue, and properly reset cache after flush.
