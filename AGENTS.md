# AGENTS.md — torch_ans

This file provides compact, high-signal guidance for OpenCode agents working in this repo. Every line answers: "Would an agent likely miss this without help?"

Scope: written for **v0.4.0** — the release that makes the native code buildable against the **libtorch stable ABI** (one prebuilt `.so` for every `torch >= 2.10`), adds the `torch_ans/ta/` compatibility layer, and replaces the per-push stream growth (`amax`+D2H, `aten::resize_`) with the Python-side capacity contract (`used_bytes`). v0.3.0 had added incremental (per-interface) JIT builds, warp-level 32-way CUDA kernels, the sparse/`"auto"` inverse-CDF lookup, interleaved alias coding and the runtime-build fallbacks. `CHANGELOG.md` (sections `[0.4.0]` / `[0.3.0]`) lists every change since 0.2.1 and `benchmark_status.md` holds the measured v0.2.1 → v0.3.0 comparison.

## Build & Install

- **Build & install**: `pip install . --no-build-isolation` compiles the extension at install time against the installed torch.
  - Without `--no-build-isolation` the package still installs, but compiles lazily on first *use* of an operator; if torch is not importable at build time the native build is skipped with a message (see `setup.py`).
- **CUDA build**: `WITH_CUDA=1 pip install . --no-build-isolation` (a visible GPU is not enough). **ROCm build**: `WITH_HIP=1`. **Skip the native build**: `SKIP_BUILD_EXT=1`.
- **Force a local build**: `TORCH_ANS_FORCE_RUNTIME_BUILD=1` ignores any pre-built `torch_ans._C` and compiles for the local torch.
- **Prebuilt stable-ABI wheel**: `WITH_STABLE_ABI=1 pip install . --no-build-isolation` (add `WITH_CUDA=1` for the CUDA flavour) builds `_C_cpu.so` (+ `_C_cuda.so`) against the *stable* ABI instead of the local torch. Verify the artefact with `python scripts/check_stable_abi_wheel.py wheelhouse/*.whl` (tag + `nm -D -u` whitelist + `readelf -d` NEEDED) and retag it before publishing: `python -m wheel tags --python-tag py3 --abi-tag none --remove wheelhouse/*.whl` (`bdist_wheel` says `cpXY` merely because `ext_modules` exists). CI: `cibuildwheel.yml`'s `build-stable-wheel` / `cross-version-load` / `cross-version-compare` (the ABI regression gate, publishes nothing). The wheels on PyPI are built by `release_wheels.yml` on every `v*.*.*` tag: `cibuildwheel` (`cp311-*`, `CIBW_BUILD_FRONTEND="build; args: --no-isolation"`, `WITH_STABLE_ABI=1`) for manylinux_2_28 x86_64 / macOS arm64 / Windows AMD64 (no Intel macOS: PyTorch ships no wheel above 2.2 for it, so it has no `torch >= 2.10`), then retagged `py3-none-<platform>` (the Linux manylinux tag is set by hand from the image, because `CIBW_REPAIR_WHEEL_COMMAND` is a no-op - `auditwheel`/`delocate` would bundle the ~hundreds of MB of `libtorch_cpu` that this wheel deliberately takes from the `torch` dependency), checked, installed and used on each platform, and uploaded. Do not upload wheels by hand. Per-push overhead A/B: `scripts/bench_stream_capacity.py` (on an RTX 2080 Ti a small CUDA push went from 157 to 39 us, the CPU one from 21 to 12 us). Build it in a clean `build/` tree: `bdist_wheel` assembles from `build/lib*`, so a leftover `_C*.so` from an ATen build ends up inside the stable wheel.
- **Clean build artifacts**: `rm -rf build/ torch_ans.egg-info/`.
- **Never leave a stale `torch_ans/_C*.so` in the tree**: it shadows `torch_ans/_C.py` completely, so the Python-side lazy/fallback machinery is bypassed and a mismatched ABI is loaded. `MANIFEST.in` excludes `*.so`.
- **Metadata**: `pyproject.toml` (`[project]`, PEP 621) is the single source of truth; `setup.py` mirrors it *only* when setuptools < 61, i.e. the `pip install . --no-build-isolation` path where `[project]` is ignored (without the mirror that build produces an `UNKNOWN` distribution with no dependencies). Bump the version in both; `tests/test_packaging_metadata.py` keeps them in sync. `MANIFEST.in` lists the native sources explicitly because setuptools does not recompute the manifest when new files appear.

## Testing

- **Run all tests**: `pytest -q` (from repo root). With coverage: `pytest --cov=torch_ans --cov-report=term-missing -q`.
- **Native C/C++ coverage**: `ENABLE_COVERAGE=1 python setup.py build_ext --inplace && ENABLE_COVERAGE=1 pytest -q`, then `gcovr -r . --html-details -o native_coverage.html`.
- **CUDA tests must go through `tests/cuda_helpers.py`** (`require_cuda_coding(self)` / `cuda_coding_skip_reason()`): `torch.cuda.is_available()` is not enough, the loaded extension also has to report CUDA via `_torch_ans_with_cuda`. Tests that only checked the GPU failed on GPU machines with a CPU-only build instead of skipping.
- **Test map** (all under `tests/`): `torch_ans_test.py` low-level push/pop/alias/inverse-CDF/CUDA; `test_high_level_api.py` `TorchANSInterface` (indexes/freqs patterns, streaming, cache, reset); `test_utils.py` bytes merge/split + PMF→CDF; `test_incremental_build.py` profiles/module names/gates + that the interface requests the right subset; `test_native_fallback.py` unloadable extension, CPU-only extension asked for CUDA, and that dunder probes never trigger a build; `test_sparse_inverse_cdf.py` dense/sparse/`"auto"` tables and the fused builders; `test_warp_cuda.py` warp 32-way and i4 CUDA kernels incl. CPU↔GPU bit compatibility; `test_index_range_check.py` out-of-range index validation; `test_packaging_metadata.py`; `test_benchmark_module.py`; `test_stable_abi.py` the prebuilt stable-ABI extension (registered operators vs `profile_op_names(None)`, bit equality with the compiled extension, the CUDA flavour incl. warp-32 and the sparse table, and that the CI cross-version floor / wheel checker still match the code); `test_capacity_contract.py` the `used_bytes` contract (Python budget vs the wrapper's own growth, mirror invariants, the older-extension fallback); `test_cross_version_load.py` one `.so` under several torch versions (`--json` / `--compare` drive the CI gate); `test_ta_headers.py` the `ta::` layer (`scripts/check_ta_headers.py` holds the compile checks); `test_tans.py` the tANS families (table invariants — spread counts, the `[ts, 2*ts)` / `[0, ts)` state ranges, `symbolTT` — round-trips across alphabets/precisions/bypass, sequential pops, the byte-string path, the high-level API, and the caps/unsupported options; on CUDA: bit equality with the CPU payload, the staged/global table paths under both `TORCH_ANS_TANS_SMEM_BUDGET` settings, and the high-level API on a device - plus the warp-level interleaved kernels at 2/4/8/32 lanes (same byte equality and cross-decoding in both directions, bypass, padding indexes, symbol counts and batches that do not fill a group/block, staging A/B, and the 32-lane capacity contract); skips when the loaded native build predates the family or the toolchain cannot build CUDA).
- **`tests/test_dynamic_build.py`'s rebuild test is guarded** — set `RUN_DYNAMIC_BUILD_TEST=1` to run it locally.
- **Benchmarks are measured locally and committed, never regenerated by CI** (CI runners are virtualised CPUs whose throughput varies by tens of percent, so the table would only show virtualisation noise). The full-matrix workflow only produces `build_status.md`. Two scripts drive it: `scripts/bench_version_matrix.py --version-label <ver> --json <out>.json` (raw-operator matrix: device × family × `num_interleaves` × symbol lookup, plus the `init_params` build steps and the end-to-end API; `--best-effort` reports operators that only exist in one release as `n/a` instead of failing) and `scripts/generate_benchmark_report.py --baseline ... --candidate ... --output benchmark_status.md`. Raw JSONs live in `benchmarks/`. `torch_ans.benchmark` (`python -m torch_ans.benchmark`) remains the user-facing CLI throughput tool; `scripts/bench_interleaves_cpu.py` (rANS *and* tANS), `scripts/bench_tans_vs_rans.py` (tANS vs rANS × lane count × `freq_precision` × alphabet, reporting bits/symbol and the per-distribution table size alongside the throughput — `benchmarks/tans_vs_rans_cpu.json`, plus the `tans8`/`freq_precision=7` supplement in `benchmarks/tans8_fp7_cpu.json` and `benchmarks/tans8_fp7_many_dists_cpu.json`; `--device cuda` runs the same matrix on the device kernels, where `--smem-budget` / `--block-threads` drive the single-lane kernels' shared-table staging and launch block size, `--warp-block-threads` the interleaved kernels' block size, and `--parallel-states` is a sweep (the batch is the dimension that decides whether interleaving pays) — `benchmarks/tans_vs_rans_cuda.json`, `benchmarks/tans_cuda_staging_off.json` / `benchmarks/tans_cuda_staging_on.json`, and for the warp-level interleaved tANS kernels `benchmarks/tans_interleaved_cuda.json` with the staging A/B in `benchmarks/tans_interleaved_cuda_smem_off.json` / `_smem_on.json`), `bench_sparse_invcdf.py`, `bench_table_build.py`, `bench_cdf_build.py` and `profile_warp_pop.py` (+ `run_ncu_warp.sh` for Nsight Compute) are the focused probes. Note the benchmark scripts import the **installed** `torch_ans` (they are run as `python scripts/x.py`, so `sys.path[0]` is `scripts/`): re-`pip install .` after changing the native code before trusting a measured number, or run them with `PYTHONPATH=$PWD` to measure this working tree instead (an older install shadows it silently otherwise).

## Key Conventions an Agent Must Know

- **Stream tensor layout**: `stream[b][0]` stores the current stream length in `int32`. Elements `stream[b][1:]` hold ANS states and bitstream data. `rans_init_stream` sets this, and the initial length is `1 + ceil(num_interleaves * sizeof(RANS_STATE_TYPE) / 4)`. A **tANS** stream puts a header there instead: one state word **per lane** (slots 1..num_interleaves, a full `int32` whatever the family's state width is) followed by the residual bit buffer and its bit count — never slot 0, which is the length word; see `tans_utils.hpp`. A fixed-width tANS state cannot absorb the bits it does not emit, so they travel in that bit buffer, which is **shared by the lanes** (only the states are per lane) and is part of the byte string. Initial length `4 * (num_interleaves + 2)` bytes (12 at one lane — the value this used to be); `_STREAM_SIZES`'s first component is "state bytes per lane", to which `_TANS_HEADER_EXTRA_BYTES` (8) is added once for the tANS families.
- **Default tensor dtype**: `torch::kInt32` (see `rans_utils.hpp` `DEFAULT_TORCH_TENSOR_DTYPE`). All CDF tables, offsets, and stream elements are `int32`.
- **Stream capacity is a contract, not a per-call computation** (v0.4.0, chosen over three alternatives: keeping the dispatcher call removes neither cost, returning a grown stream changes the public signature and every call site, and a strict pre-reservation loses push's self-growing behaviour): `TorchANSInterface` reserves the capacity (`utils._stream_budget` mirrors the worst-case arithmetic of `torch_ans/stream_capacity.hpp::ans_ensure_stream_capacity`, which `rans_push` *and* `tans_push` call — the bound is family independent: at most `freq_precision` bits per symbol plus the bypass chunks) and passes it as the trailing `used_bytes` argument; with it the native wrapper only *compares* and raises (`ValueError`) instead of reading `stream[:, 0]` back (a blocking D2H on CUDA) and calling `aten::resize_`. `used_bytes=-1` (the default) keeps the old self-growing behaviour — that is what direct operator calls in tests/scripts get, and what an extension compiled before this release still gets. The mirror (`_mirrored_stream` / `_mirrored_capacity` / `_mirrored_used_bytes`) is dropped when the tensor or its column count changes and after every pop (a pop rewinds the length word), so it is always an *upper* bound. The rule that follows: **one writer per stream** — a second interface writing the same tensor without changing its column count can make the first one's mirror too small, which fails loudly rather than silently. Keep `_stream_budget` and `rans_push`'s arithmetic in step: `tests/test_capacity_contract.py` uses the wrapper's own growth as the oracle.
- **CDF format**: CDF tables have shape `(num_distributions, max_symbols + 2)` (`+ 1` without bypass, `+ 2` with bypass). The last entry is always `2^freq_precision` (e.g., 256 for precision=8).
- **Bypass coding**: When `bypass_coding=True`, PMF/CDF is extended with a tail mass of `1e-10` (or `1/(1<<freq_precision)`) to handle out-of-range symbols. An out-of-range symbol is zig-zag encoded into a raw value in the symbol dtype, so its distance from `[offset, offset + cdf_size - 2)` must stay below `2^(bits-2)` (~2^30 for `int32`); further out it overflows silently.
- **`TorchANSInterface` impl mapping** (in `utils.py`):
  - `"rans64"` → `rans64_init_stream` / `_push` / `_pop`, `freq_precision` capped at 31.
  - `"rans32_16"` → `rans32_16_*`, capped at 15 — **must be matched before `"rans32"`** since `"rans32_16".startswith("rans32")` (0.2.1 got this wrong, silently running the rans32 operators).
  - `"rans32"` → `rans32_*`, capped at 23.
  - `"tans32"` (uint32 state + uint16 stream words) and `"tans16"` (uint16 + uint8) → `tans*_init_stream` / `_push` / `_pop`, `freq_precision` capped at 15 — the limit of the encoder's 16.16 fixed point (`nbBits = (state + deltaNbBits) >> 16` with `minStatePlus ∈ (2**L, 2**(L+1)]`), *not* of the state width. `"tans8"` (uint8 + uint8) → capped at 7 (its state has to hold `[2**L, 2**(L+1))`) and is the small-table tier. tANS is **table-driven**: `alias_sampling` / `inverse_cdf_precision` do not apply (the tANS table *is* the symbol lookup — the existing key checks reject them). `freq_precision` **is** `table_log`, i.e. the spread table has `2**freq_precision` slots per distribution (`3 * 2**freq_precision + 2 * cdf_row` int32 words for both directions, built by the host-side `tans_build_tables` in `init_params` — on the CPU even for a CUDA interface, then moved to `self.device` — and carried in the `cdfs` slot of push *and* pop), so a tANS interface is much cheaper at a small `freq_precision` — that, and not the state width, is what the family choice is about. **Interleaved tANS (1/2/4/8/32 lanes)** keeps one state per lane in the header (slots `1..ilv`) and shares the single bit buffer (slots `ilv+1`, `ilv+2`) between the lanes, so the header — and the initial length word — is `4 * (num_interleaves + 2)` bytes; the lane of a symbol is its index % `num_interleaves`, and push/pop walk the lanes in mirrored order, exactly like `rans_cpu.cpp`. **On CUDA** (`torch_ans/tans_cuda.cu`, included by `setup.py`'s stable-ABI CUDA source list and globbed by the ATen/JIT paths) the same three families run with one thread per stream row at one lane and with one *lane group* per row above it (the warp kernels in `torch_ans/tans_warp_cuda.cuh`, see the tANS warp bullet below): `tans_push` / `tans_pop` need no device branch, because the launcher routes `NUM_INTERLEAVES > 1` to those kernels itself. Both kernel families are the CPU loop rebased onto the device, so CPU and CUDA produce **byte-identical** payloads for the same table at every interleave factor (`tests/test_tans.py` compares the byte strings, not just the decoded symbols, and cross-decodes both ways). The lookup table is staged into shared memory when the whole table fits `TORCH_ANS_TANS_SMEM_BUDGET` (default 16 KiB/block, `0` disables; compile-time `USE_SHARED_TABLE` instantiations and the whole-table-or-nothing rule copied from A9 in `rans_warp_cuda.cuh`) and the launch block size is derived from the batch size (`TORCH_ANS_TANS_BLOCK_THREADS` overrides) — the measurements behind both knobs are in the `tans_num_threads_per_block` comment and `benchmark_status.md` — including the low-distribution sweeps (8 and 4 distributions, i.e. tables of 6-48 KB that *do* fit) which show the staging is a wash with many blocks and 1024-symbol rows (0.92-0.97× of the global path) and a real gain with few blocks and long streams (+4.6-5.4% encode / +3.1-3.6% decode at 64 streams × 16K symbols).
  - `num_interleaves` ∈ {1, 2, 4, 8} for every family (rANS *and* tANS), plus **32 for `rans32_16` and the three tANS families**; the suffix is `""` / `_i2` / `_i4` / `_i8` / `_i32`. 32-way is the full-warp group of the CUDA warp kernels — `rans32_16` only among the rANS families, all three tANS families, whose CPU kernels implement it from the same lane loop, so the operator set is the same on both devices; the alias variants exist for 1/2/4/8 only, and tANS has none.
  - The supported `(family, num_interleaves)` combinations live in `_dynamic_build.SUPPORTED_INTERLEAVES` / `ALIAS_INTERLEAVES` / `INVCDF_INTERLEAVES`; `utils.RANS_IMPL_OP_NAMES` / `RANS_ALIAS_OP_NAMES` / `RANS_INVCDF_POP_OP_NAMES` are derived from them and **the keys double as the validation of what each impl supports** (an unsupported combination raises before a useless build is started). Operators are resolved against the instance's own module, `self._native` — never via module-level globals, because an incrementally built module only contains the selected subset.
- **Incremental (per-interface) JIT builds**: the runtime build compiles only the operators an interface needs, and `utils.py` / `_C.py` / `_lazy_C.py` are lazy (nothing compiles at import). The chain is: `TorchANSInterface.__init__` → `_build_profile()` builds a `BuildProfile(family, interleave, alias, invcdf)` → `utils._native_module(profile, incremental_compile, require_cuda)` → `_lazy_C.ensure_module(profile)` → `_dynamic_build.profile_module_name/profile_defines/profile_op_names` → `build_extension(defines=...)`. `incremental_compile=False` (or `TORCH_ANS_INCREMENTAL_COMPILE=0`) selects the full build; `incremental_enabled()` reads the argument first, then the env var. **Four** places must stay in sync when the operator set changes:
  - `torch_ans/ans_bindings.hpp` — the pybind11 bindings *and* the stable-ABI schema/impl lists, both gated by `#if TORCH_ANS_WITH_*` (this replaced the `TORCH_EXTENSION_RANS_BINDINGS` macro, which could not contain preprocessor conditionals). The two lists must stay identical to each other except for the two `py::bytes` operators, which only the pybind list has; `tests/test_stable_abi.py` asserts that agreement against `profile_op_names(None)` whenever a prebuilt stable extension is loaded, so a drift shows up as a test failure rather than an `AttributeError` at first use;
  - `torch_ans/rans_cpu.cpp` / `rans_cuda.cu` / `tans_cuda.cu` — the *explicit instantiation* blocks with the same gates (`TORCH_ANS_INST_*`, `TORCH_ANS_CUDA_INST_ILV*`, `TORCH_ANS_INST_TANS_*` and the `*_CUDA` variants); the wrappers in `rans.hpp` / `tans.hpp` only see declarations, so every bound combination needs an instantiation in the TU that defines it, and `rans_cuda.cu` must mirror every combination the bindings create or the `.so` gets an undefined symbol and nothing imports. `tans_cuda.cu` instantiates one pair per interleave factor (behind the same `TORCH_ANS_WITH_INTERLEAVE_*` gates the CPU side uses), and for `NUM_INTERLEAVES > 1` its launcher body returns the warp launcher — instantiating the caller instantiates the callee, so the warp kernels need no instantiation macro of their own. It is also the third entry in `setup.py`'s explicit stable-ABI CUDA source list, next to `rans_cuda.cu`;
  - `torch_ans/_dynamic_build.py` — `FAMILY_MACROS` / `FAMILY_TAGS` / `OP_SUFFIX` / `SUPPORTED_INTERLEAVES` / `ALIAS_INTERLEAVES` / `INVCDF_INTERLEAVES` / `COMMON_OPS` and `profile_op_names` (the names a module is expected to export; they are also what an already loaded module is checked against with `hasattr` before it is reused, so never under-report — note `profile_op_names(None)` asks for `invcdf=True, alias=True` and relies on the `*_ok` arguments to leave the tANS families out of both).
  `tests/test_incremental_build.py` checks the Python side and that the gates exist in `ans_build_config.hpp`. A module name is the build cache key (`torch_ans_C`, `torch_ans_C_common`, `torch_ans_C_r64_i4_invcdf`, `torch_ans_C_tans8`, ...), so a profile must map to exactly one define set; any loaded module that already exports the requested names (in particular the full build) is reused. The gates are `TORCH_ANS_WITH_RANS64/_RANS32/_RANS32_16`, `TORCH_ANS_WITH_TANS32/_TANS16/_TANS8`, `TORCH_ANS_WITH_INTERLEAVE_2/_4/_8/_32`, `TORCH_ANS_WITH_ALIAS`, `TORCH_ANS_WITH_INVCDF`; they default to 0 only under `TORCH_ANS_INCREMENTAL_BUILD` and to 1 otherwise. `tans_build_tables` is deliberately ungated (all three tANS families share one table tensor, so it is in `COMMON_OPS`); its kernel lives in `tans_cpu.cpp` together with the three families' explicit instantiations (`TORCH_ANS_INST_TANS_*`).
- **Runtime build fallbacks — a compiled extension must never be a dead end**:
  - A prebuilt libtorch-stable-ABI extension (`torch_ans/_stable_C.py`, migration stages 3-4) wins over compiling: `_lazy_C.ensure_full/ensure_module` return it as soon as it loads, for any profile, so a wheel with a prebuilt `.so` never builds anything. Every failure (old torch, missing file, `torch.ops.load_library` refusing it, a CUDA request without a CUDA `.so`) is a warning plus the normal build, never an error. `TORCH_ANS_NO_STABLE_ABI=1` disables it, `TORCH_ANS_STABLE_LIB_DIR` points the search somewhere else.
  - An extension that cannot be imported (built against another torch / different ABI) makes `utils._import_native_c` warn and fall back to the shim (`torch_ans._lazy_C`), which compiles one for the local torch.
  - A CPU-only extension asked to code CUDA tensors does not fail with the bare C++ `"not compiled with GPU support!"`: `TorchANSInterface._ensure_native_for` warns, re-resolves with `require_cuda=True` and, if that is impossible, raises `RuntimeError(_CUDA_UNAVAILABLE_HINT)` with the exact install/rebuild commands. `module_has_cuda()` reads the compiled-in `_torch_ans_with_cuda` flag (set in `lib.cpp`), falls back to `BUILD_WITH_CUDA` in `_torch_build_version.py` for extensions older than the flag, and never probes the shim (its `__getattr__` would compile everything).
  - In `_lazy_C`, a CUDA-capable and a CPU-only build of one profile coexist (cache key `<name>::cuda`, build name `<name>_cuda`) and `_usable()` never reuses a known-CPU-only module when CUDA is required. Dunder probes raise `AttributeError` without building — that is what keeps `import torch_ans.utils` lazy (`from ._lazy_C import ...` probes `__path__`).
  - The CUDA toolchain outcome is remembered in a `cuda_build_state` file inside the torch extensions cache dir, keyed by `torch_ans_cuda_toolchain` (deliberately not the module name, so profiles share it): `cpu` means "every CUDA configuration failed, build CPU-only directly next time", `ccbin:<path>` means "only this host compiler works". Delete the file after fixing the toolchain to retry. The same module also patches torch's `FileBaton` so a lock left behind by a killed build goes stale after 600 s instead of deadlocking every later import, and resets torch's JIT versioner so a retry reuses the base module name.
  - A macOS OpenMP module can build, link and import perfectly and still abort the process on its first parallel op (SIGABRT inside `rans_pmf_to_quantized_cdf`, no exception, no diagnostic — the Homebrew libomp it links is a second OpenMP runtime next to libtorch's; seen with torch 2.14 on arm64, while 2.13 and older work). No build- or load-time check can see that, so `_openmp_coding_survives` runs that operator once in a **child process** (where the crash is an exit status) before accepting the variant, and the build falls back to the flags without a second runtime — the ones `setup.py` has always used on macOS. The outcome is remembered in `openmp_build_state`, keyed by `torch_ans_macos_openmp`; delete it to try OpenMP again.
- **Sparse inverse-CDF symbol lookup** (`inverse_cdf_precision` int or `"auto"`, a *pop*-only op variant):
  - `table_precision < freq_precision` builds a sparse table of `2**q` entries where entry `i` answers for bucket start `i << (freq_precision - q)`; that start is a lower bound of the queried `cum_freq`, so the decoder closes the remaining gap with a **branch-free** window load (`rans_invcdf_advance`, `RANS_INVCDF_WINDOW`=2 parallel cdf entries, index-clamped to `cdf_size - 1`) and a rare `while` remainder (a bucket can span many symbols when the pmf is flat). Dense (`= freq_precision`) is exact but tens of MB for many distributions and thrashes the cache — the sparse/`auto` table is the fastest CPU decode lookup measured.
  - `"auto"` defers the precision to `init_params` (`utils.auto_inverse_cdf_precision`): no table at all for alphabets < 64 (`min_alphabet`), otherwise `q ≈ alphabet_size.bit_length() - 1` (a ~2-step walk), shrunk by one when `alphabet + 2**q` exceeds `AUTO_INVERSE_CDF_SHARED_BUDGET_BYTES // (num_distributions * itemsize)` (16 KiB, mirroring the staging budget in `rans_warp_cuda.cuh`). The chosen `q` happens to be the CPU optimum too. When the heuristic drops the table, `init_params` swaps `ans_decode_func` back to the divided-search op.
  - The pop op's `inverse_cdf_precision` kwarg (`-1` = none) reaches the kernel via `TorchANSInterface._decode_extra_kwargs`. `utils.build_cdf_with_inverse_table` / `native.rans_build_inverse_cdf` build `cdf ++ table` in one op (one allocation, no separate table, no `cat`) and `_bucket_starts` caches the `arange << shift` grid — both are on the `init_params` hot path of the `dist_freqs` API, where `init_params` runs per encode/decode call. `inverse_quantized_cdf` uses a batched `torch.searchsorted` (bit-identical to the old broadcast compare-and-count, which materialised an `(N, 2**q, M)` intermediate).
  - `rans_build_inverse_cdf` and the fused `rans_pmf_to_quantized_cdf` are **common ops** (not gated), because every interface needs them.
- **Alias sampling** (`alias_sampling=True`, `*_alias_*` ops) is CPU-only, interleaved for 1/2/4/8, and the *slowest* lookup: use `inverse_cdf_precision="auto"` instead. If you do touch it: (a) `rans_alias_build_table` only accepts `cdfs_sizes - 1 == 2**symbol_precision` (e.g. alphabet 255 with bypass, cdf row 257) and now **raises instead of silently emitting a broken table** (the interface raises `ValueError` before calling it when the row is not a power of two); (b) the bucket index must stay a *shift* — `cut_size` is a power of two so `cum_freq / cut_size` is a division by a compile-time-unknown value, i.e. the non-pipelined divider, which is what caps its interleaving gain; (c) push reads the *remap* table (32 MB for 256 distributions) while pop reads the 4-field alias table — the two are different tensors (`rans_alias_build_table` returns both, the interface keeps the pop one in `self.cdfs_with_alias_table`) and mixing them up decodes garbage.
- **Warp-level interleaved CUDA kernels** (`torch_ans/rans_warp_cuda.cuh`): one lane group (`NUM_INTERLEAVES` lanes of a warp, `WARP_NUM_THREADS_PER_BLOCK`=256) codes one batch row with a shared bitstream cursor held in registers; `__ballot_sync`/`__shfl_xor_sync` place renorm words (no shared memory and no `__syncthreads` for that; the CDF rows and lookup tables are staged into shared memory separately). **Bit-compatible with the CPU interleaved implementation**: symbol `s` lives on lane `s % NUM_INTERLEAVES`, push walks groups high→low appending forward with lane N-1→0 order inside a group (bypass raw-value runs first, then symbol pushes), pop mirrors it backward. Changing either side's word order breaks CPU↔GPU stream compat — `tests/test_warp_cuda.py` guards this. Instantiated only for rans32_16 (`uint32` state + `uint16` stream, at most one word per renorm, which the ballot/prefix scheme relies on); `rans_push/pop_indexed_cuda` raises `TORCH_CHECK(false, "torch_ans: CUDA interleaved coding is only supported for the rans32_16 variant ...")` for any other family, and the i2/i4/i8 variants route to power-of-two sub-warp groups while i32 uses the full warp.
- **Warp-level interleaved tANS kernels** (`torch_ans/tans_warp_cuda.cuh`, included by `tans_cuda.cu` the way `rans_warp_cuda.cuh` is by `rans_cuda.cu`): one lane group of `NUM_INTERLEAVES` lanes codes one row, and the structural difference to the rANS kernels is the one the family forces — a fixed-width tANS state cannot absorb the bits it does not emit, so the group shares **one** bit buffer and **one** payload cursor instead of owning words per lane. The per-lane half is parallel (encode: the `symbolTT` + `nextState` loads; decode: the two decoder planes — the divergent table loads the warp amortises, plus coalesced `symbols`/`indexes` loads at consecutive indices, which the one-thread-per-row kernel cannot have); the bit layer is committed in lane order (push lane N-1→0, pop lane 0→N-1) by broadcasting each lane's field with `__shfl_sync` and letting **every** lane apply the same update, with only lane 0 storing the flushed word (`tans_warp_append` — the duplicate store would be the same value, but a race). Bypass digits are the inherently sequential exception: each lane's digit decomposition is precomputed with the writer simulation (`tans_warp_raw_digit_count`, the tANS twin of `rans_warp_simulate_raw_push`) and the block is skipped by one `__ballot_sync` when no lane is a sentinel (A5); the decode side keeps `rans_warp_cuda.cuh`'s lane-ascending walk for the same reason. All of it mirrors `tans_cpu.cpp`'s interleaved path bit for bit, head/tail (`num_symbols % N`) included, which is what `tests/test_tans.py` checks by comparing byte strings and cross-decoding. Four things keep the shared bit layer affordable, and all four were missing before 2026-09-20 (when 32 lanes measured *slower* than one lane): (1) the bit layer is a **32-bit** window in the warp kernels (`TansWarpBitWriter` / `TansWarpBitReader`), not the shared `TansBitWriter`'s 64-bit one — at rest it holds < `STREAM_BITS` bits and one digit is ≤ 15 bits, so ≤ 31 bits are ever live, and the update runs once per lane per group in every lane; (2) one broadcast per lane carries everything the serial section needs — `tans_warp_pack_lane` packs the low 15 bits of the state (all an append can use), `nb_bits`, the validity and the bypass flag into one `__shfl_sync` instead of two; (3) **the unrolled serial section is only emitted up to 8 lanes** (`tans_warp_roll_serial`, ≥16 lanes rolls it) — at 32 lanes the unrolled body cost 229 registers/thread, i.e. one 256-thread block per SM; (4) **decode does not walk at all when no lane bypasses** (`tans_warp_parallel_read`, ≥4 lanes): a lane's bits are a function of the prefix sum of the lanes' `nbBits`, so `TansWarpBitWindow` lets every lane read its own bits directly (≤2 words) instead of replaying the group's takes. Push keeps its walk, and that is not laziness: the bits have to be *written* and a word mixes several lanes, so no lane owns a word the way it owns a read — rANS avoids the whole problem because its lanes renormalize whole words. `tans_table_staging` / `tans_stage_table` / `TORCH_ANS_TANS_SMEM_BUDGET` are shared with the single-lane kernels; the block size is derived from the batch and the lane count (`TORCH_ANS_TANS_WARP_BLOCK_THREADS` overrides), because a group codes one row and a fixed 256-thread block leaves most SMs idle for a small batch. **Measured** (RTX 2080 Ti, 64 distributions, table in *global* memory, 4M symbols, µs per run; before → after in `benchmarks/tans_interleaved_cuda.json` vs `benchmarks/tans_interleaved_cuda_optimized.json`, `tans32` at `freq_precision=7`): 32 lanes encode 228356 → 88000 µs at 8 rows (2.59×), 6616 → 4963 at 512 rows, and decode 203334 → 17548 (11.6×), 4619 → 2126, 6064 → 3521 (1.72×) — 32 lanes is no longer a regression, it is the fastest factor whenever the batch does not fill the device. At 4096 rows encode is flat (6456 → 6875, 0.94×): there the 32-lane row simply codes more bytes (6.96 vs 5.99 bits/symbol, mostly the 136-byte header). rANS' 32-way warp path is still much faster at a tiny batch (227/209 MB/s vs tANS' ~48/239) because its lanes own their words; at 4096 rows the two are within a few percent.
- **CPU interleaving invariants — do not undo these, they are what makes `num_interleaves>1` faster instead of slower** (measured ~1.25-1.4x encode / ~1.8-2.1x decode at `num_interleaves=4`; see CHANGELOG `[0.3.0]` and `benchmark_status.md`):
  - `APPEND_STATE_TO_STREAM_IF` / `POP_STATE_FROM_STREAM_IF` (`rans_utils.hpp`) are branch-free: the encode side stores one word **past the cursor** speculatively and only commits the cursor with a `cmov`. Every stream buffer must therefore keep **one word of slack** — `rans_init_stream` adds `+2` elements and `rans_push`'s `safe_byte_length` adds `(NUM_INTERLEAVES + 1)` words. The garbage word is overwritten by the next append and is beyond the stored length, so streams stay bit-identical to the branchy CUDA path.
  - The interleaved kernels (`rans_push_indexed_cpu` / `rans_pop_indexed_cpu`) keep the states in **register-resident locals with compile-time lane indices** (`constexpr_for`). A runtime index (`states[i % NUM_INTERLEAVES]`) or a variable-index access in the head/tail loop spills the whole array to the stack and destroys the gain. The head/tail loops use `state_mem` directly for this reason.
  - Loop-invariant scalars and the cdf pointers/strides are copied into locals **inside** the `parallel_for` body; the lambda captures by reference, so values whose address escapes are reloaded after every stream store (this alone used to chain all lanes).
  - Renormalization and the symbol lookup must stay branch-free, and push must not use integer division (see `rans_divmod`, FP divide + exact fix-up). The interleaved pop searches **all lanes step by step** (one batched monotone search across the group), not lane by lane.
  - The inverse-CDF gap closing must stay branch-free too (`rans_invcdf_advance`, see the sparse-table bullet above). With this, `inverse_cdf_precision="auto"` + `num_interleaves=4` is the fastest CPU decode configuration measured; a *dense* table is not.
  - **Every push/pop combination bound in `ans_bindings.hpp` needs a CUDA instantiation** in `rans_cuda.cu` (the wrapper in `rans.hpp` refers to the CUDA template whenever `WITH_CUDA` is defined). A missing one does not fail the build — it leaves an undefined symbol that makes the *whole* module fail to import. Add the instantiation for any new binding, even if the combination is unsupported on CUDA (unsupported ones raise a clear error at call time; interleaved CUDA coding is rans32_16-only).
  - The warp push kernel (`rans_warp_cuda.cuh`) takes `USE_ALIAS_SAMPLING_CDF` and **must** apply the alias remap in the symbol push (`alias_remap_ptr[(state % freq) + start]`, where the remap starts at `cdf_ptr + cdf_size`) — it used to ignore the flag and silently emit a plain rANS stream (regression test: `test_cuda_alias_interleaved_roundtrip`).
  - `num_interleaves=32` is CUDA-only in practice: on CPU it is ~0.8x encode (register pressure); use 4 or 8.
  - `scripts/bench_interleaves_cpu.py` measures the end-to-end API; a raw-op probe is faster to iterate with (write a throwaway one).
- **Dynamic runtime build**: If the native extension `_C` is not present, the first native operator use triggers runtime compilation via `pybind11`/`torch.cpp_extension` — by default only for the operators the interface asks for (see the incremental-build bullet); `torch_ans._C.<op>` / `from torch_ans._C import <op>` compile the *full* extension, and `torch_ans.utils.__getattr__` resolves the legacy operator names that used to be imported there (`_legacy_native_op`) on first attribute access. `_dynamic_build.build_extension` detects CUDA availability **before** importing `torch.utils.cpp_extension` (that import makes the process's first CUDA call, and doing it under `CUDA_VISIBLE_DEVICES=""` permanently disables CUDA for the process), passes `-DWITH_CUDA` to nvcc explicitly (torch forwards `extra_cflags` to the C++ compiler only and, unlike `WITH_HIP`, does not define it itself), and only falls back to a CPU-only build through flag variants that never define `WITH_CUDA` (a cpp-only build with it has undefined symbols and fails to load).
- **CUDA availability**: CUDA coding tests are skipped when `torch.cuda.is_available()` is `False` **or** `module_has_cuda(torch_ans._C) is False` (see `tests/cuda_helpers.py`).

## Environment & Gotchas

- **Env vars**: `WITH_CUDA=1` / `WITH_HIP=1` (build with GPU support), `FORCE_CUDA=1` / `FORCE_ROCM=1` (ignore `torch.cuda.is_available()`), `SKIP_BUILD_EXT=1` (no install-time build), `TORCH_ANS_FORCE_RUNTIME_BUILD=1` (ignore a pre-built extension), `TORCH_ANS_INCREMENTAL_COMPILE=0` (build every operator), `TORCH_ANS_STRICT_CHECK=1` (promote the build/runtime torch mismatch warning to `ImportError`), `RUN_DYNAMIC_BUILD_TEST=1` (unlock the guarded rebuild test), `ENABLE_COVERAGE=1` (gcov-instrumented extension).
- **Torch version mismatch**: The build-time torch version is written to `torch_ans/_torch_build_version.py`. At runtime a differing major.minor warns by default (`__init__.py`); `TORCH_ANS_STRICT_CHECK=1` makes it an `ImportError`.
- **nvcc vs host compiler**: `nvcc <= 12.1` may cannot parse the `std::function` headers of `libstdc++` from GCC >= 11.4 (`std_function.h: parameter packs not expanded with '...'`); `nvcc >= 12.2` or an older `-ccbin` (`g++-10`/`g++-9`/`g++-8`) fixes it, and the runtime build tries the older compilers automatically and remembers the working one. Also make sure the toolkit version matches the one the torch wheel was built with (e.g. nvcc 11.8 for `torch ...+cu118`).
- **C++ standard**: supply `-std=c++17` only for torch 1.x. torch >= 2 appends its own standard (up to C++20) later on the command line and a user-supplied `-std=` would override it.
- **macOS**: OpenMP comes from Homebrew `libomp` (`-Xpreprocessor -fopenmp -lomp`); without it `at::parallel_for` runs on torch's own thread pool. Xcode 16 also needs `-Wno-invalid-specialization` for torch 2.7 headers. The runtime build handles both, and probes the OpenMP variant in a child process (once per torch version) because that variant can abort at use time (see the runtime-build fallbacks above).
- **CPU parallelism**: `torch.set_num_threads()` controls the OpenMP parallelism of push/pop; OpenMP is enabled by both build paths (GCC `-fopenmp`, MSVC `/openmp`, Homebrew libomp on macOS).
- **Python version**: Requires Python >= 3.7. CI covers 3.7 / 3.9 / 3.11 against torch 1.10.1 / 2.1.1 / 2.7.1 on Linux, macOS and Windows (+ an ARM64 Linux job and a lazy-compile job that installs without a compiler).

## Directory Ownership

- `torch_ans/rans*.cpp`, `rans*.hpp`, `rans*.cu`, `rans*.cuh` — C++/CUDA sources, written against the `ta::` compatibility layer (they must not call ATen directly any more); adding new variants requires the pybind bindings *and* the stable schemas/impls in `ans_bindings.hpp`, the matching instantiations in `rans_cpu.cpp`/`rans_cuda.cu` and the profile tables in `_dynamic_build.py` (all gated together; `tests/test_stable_abi.py` checks the stable list against `profile_op_names(None)`).
- `torch_ans/ans_build_config.hpp` — the `TORCH_ANS_WITH_*` feature gates and the explicit-instantiation macros (spelled in `ta::Tensor` and self-sufficient, because `rans_cuda.cu` includes it directly); `torch_ans/ans_bindings.hpp` — the gated pybind11 binding list (ATen build) *and* the stable schema strings + boxed impls (`torch_ans_register_schemas` / `_init_impls` / `_cpu_impls`); `torch_ans/lib.cpp` — the module entry point for both flavours (pybind11 module, or `STABLE_TORCH_LIBRARY` registration) and the `_torch_ans_with_cuda` capability flag.
- `torch_ans/rans_utils.hpp` — shared coding primitives (`APPEND_STATE_TO_STREAM_IF`, `rans_divmod`, `rans_invcdf_advance`, `constexpr_for`) and `DEFAULT_TORCH_TENSOR_DTYPE`; the torch include and the dtype macro are behind `#ifndef TORCH_ANS_STABLE_ABI` so the same algorithm core compiles torch-free for the libtorch-stable-ABI build (`poc/stable_abi/csrc/poc_cuda.cu` and `_ops.cpp` include it that way) — keep that guard intact and do not add a torch dependency above it. `torch_ans/rans_warp_cuda.cuh` — the warp-level CUDA kernels.
- `torch_ans/ta/` — the `ta::` compatibility layer between today's ATen build and the future libtorch-stable-ABI build (`torch_api.hpp` dispatches on `TORCH_ANS_STABLE_ABI` to `torch_api_aten.hpp` / `torch_api_stable.hpp`; `view.hpp` is the shared POD replacement for the accessors). `rans.hpp`, `rans_cpu.cpp`, `rans.cpp`, `ans_bindings.hpp` and `lib.cpp` all go through it now (migration stages 1-4); it is compile-checked in both modes (and with nvcc) by `scripts/check_ta_headers.py` / `tests/test_ta_headers.py`. Keep the stable backend free of `at::`/`c10::` symbols and of `<torch/extension.h>`: that independence is what the prebuilt wheel sells.
- `poc/stable_abi/` — runnable libtorch stable ABI POC (22 tests, CPU + CUDA); the `ta::` layer and the prebuilt `.so` were derived from it, so its results are the reference for changes to `ans_bindings.hpp` / `lib.cpp` / the two `py::bytes` operators (the two build modes have to stay bit-identical).
- `torch_ans/utils.py` — Python API layer; `TorchANSInterface` is the main entry point. Changing native signatures requires updating the operator names (`RANS_*_OP_NAMES`), the call sites and the C++ bindings/instantiations.
- `torch_ans/_dynamic_build.py` — runtime build; owns the BuildProfile → module name / defines / expected operator names mapping and the CUDA-toolchain/fallback logic. `torch_ans/_lazy_C.py` — the shim that builds and caches one module per profile; `torch_ans/_C.py` — the thin forwarder that keeps `import torch_ans._C` working when no compiled extension is present; `torch_ans/_stable_C.py` — loads a prebuilt libtorch-stable-ABI extension with `torch.ops.load_library` (found next to the package or in `$TORCH_ANS_STABLE_LIB_DIR`) and implements the two `py::bytes` operators in Python (`_lazy_C.ensure_*` prefers it over compiling; any failure falls back to the runtime build).
- `tests/` — test suite (see the test map above); `tests/cuda_helpers.py` — the shared CUDA-availability gate; `tests/test_ta_headers.py` — the `ta::` compatibility layer (static checks + the compile checks below); `tests/test_stable_abi.py` — the prebuilt stable-ABI extension (skipped when there is none): registered operators vs `_dynamic_build.profile_op_names(None)`, that `_lazy_C.ensure_*` prefers it, and bit-exact agreement with the compiled extension incl. the Python `bytes` operators.
- `scripts/` — benchmark and profiling drivers (`bench_version_matrix.py` + `generate_benchmark_report.py` are the release-comparison pair); `scripts/check_ta_headers.py` — compiles the `ta::` layer in both build modes with g++ and, when a usable nvcc exists, with nvcc; `benchmarks/` — the committed raw JSON behind `benchmark_status.md`.
- `pyproject.toml`, `setup.py`, `MANIFEST.in` — build configuration and packaging; `setup.py` conditionally builds CUDA/ROCm extensions from the env vars and writes `_torch_build_version.py`.
